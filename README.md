# 电商经营分析 Agent（E-commerce Analytics Agent）

面向**电商运营**的数据分析 Agent：上传店铺导出的订单表（Excel / CSV），用中文提问（可以连续追问），Agent 自动完成 **检查数据质量 → 按需加载 Skill → 规划分析步骤 → 编写并执行 Python 代码 → 出错自动修正 → 生成报告 → 核对报告里的每个数字**。

## 面向谁、解决什么问题

| | 说明 |
|---|---|
| **用户** | 中小电商 / 跨境电商的运营人员：每天要看销售额、退货、广告效果，但不一定会写 SQL 或 Python |
| **痛点 1：数据脏** | 平台导出的订单表常有重复订单、缺失值、录入错误（如单价多打两个 0），直接汇总会把结论带偏 |
| **痛点 2：口径乱** | “退货率”按单数还是按金额？ROAS、ACOS 怎么算？不同人算出来不一样，没法对比 |
| **痛点 3：不敢信 AI** | 通用聊天机器人会“编”数字，运营拿去汇报有风险 |
| **本项目的做法** | 数据清洗 Skill 先识别并剔除异常数据；电商指标 Skill 统一指标口径；所有数字由代码真实算出，报告里的每个数字都会被程序核对出处 |

典型问题：“各品类的销售额和退货率是多少？哪个品类最值得重点投入？”“哪个店铺的广告投入产出比最高？”“每月销售额有没有旺季？”“评分低的订单有什么共同特点？”

项目重点不在“让 AI 回答问题”，而在于让 AI 的输出**可执行、可追溯、可校验**：
- AI 写的代码先经过安全检查，再放进独立进程运行，有超时限制；
- 代码报错时把错误信息交回模型修改，最多重试 N 次；
- 用 **Skill** 把数据清洗规范、电商指标口径等专项知识按需交给模型；
- 报告只能使用真实算出的数字，程序会逐个核对，对不上的标出来提醒人工复核；
- 每一步的代码、结果、报错都有记录，可以导出 HTML 报告和 JSON 日志；
- 每次调优的问题、原因、改进和效果都记录在 [docs/调优记录.md](docs/调优记录.md)。

> 通用表格也能分析，但 Skill、示例数据和评测集都是围绕电商订单设计的，这是项目的定位。

## 前后端结构

```
浏览器（React 前端，frontend/）
   │  fetch：/api/sessions、/api/sessions/{id}/ask ……
   ▼
后端（FastAPI，api/main.py）── 密钥只在这里（.env）
   │  调用
   ▼
Agent（analyst/）── 规划-执行 / 工具调用 / 经 MCP 调用
```

| 接口 | 作用 |
|---|---|
| `POST /api/sessions` | 新建对话 |
| `POST /api/sessions/{id}/sample`、`/upload` | 使用示例数据 / 上传 CSV、Excel |
| `POST /api/sessions/{id}/ask` | 提问：用 **SSE**（服务器推送事件）一边分析一边推送进度，最后推送完整结果 |
| `POST /api/sessions/{id}/clear` | 清空对话（短期记忆） |
| `GET / POST / DELETE /api/preferences` | 长期偏好 |
| `GET /api/runs/{id}/report.html`、`/log.json` | 下载报告、运行日志 |

为什么用 SSE：一次分析要 20～40 秒，如果等全部做完才返回，页面会一直空白；SSE 让后端每完成一步就推一条进度（“正在执行第 2 步……”），前端立刻显示。会话保存在后端内存里，适合单人本地使用。

## 工作流程

```
用户问题 + 数据（+ 前几轮对话的结论）
      │
      ▼
① 感知：统计行数、类型、缺失、重复、负数、极端值（profiler.py）
      │   只把概况、前 5 行样例和前几轮结论发给模型，不上传整张表
      ▼
② 选择 Skill：根据数据状况和问题关键词，决定加载哪些专项规则（skills.py）
      │
      ▼
③ 规划：模型把问题拆成 3～5 个计算步骤；“汇总/给建议”类步骤由程序去掉，交给报告
      │
      ▼
④ 对每一步循环：
      写代码 ──► 静态安全检查 ──► 子进程执行 ──► 成功？──是──► 下一步
         ▲            │ 不通过          │ 报错/无结果
         └──── 把错误交回模型修改 ◄─────┘   （最多重试 N 次）
      第一步清洗后的数据交给后续所有步骤共用，保证口径一致
      │
      ▼
⑤ 报告：模型根据各步结果写结论、依据、数据质量说明、建议与局限；
      │  步骤说明与数字矛盾时以数字为准并更正
      ▼
⑥ 校验：报告中的数字逐个与计算结果比对，找不到出处的标出（validator.py）
      │
      ▼
⑦ 独立审查：另起一次模型调用，只看“问题 + 步骤结果 + 报告”，专门找结论与数字矛盾之处
         发现严重矛盾 → 把问题交回写报告的模型改一次 → 重新核对数字（reviewer.py）
```

### 两道检查的分工

| | ⑥ 数字核对（程序） | ⑦ 独立审查（另一个模型角色） |
|---|---|---|
| 查什么 | 报告里每个数字在计算结果里有没有出处 | 排名、趋势、谁高谁低、形容词是否和数字矛盾 |
| 能抓到 | “预计增长 30.5%”这种编出来的数字 | 数字都对、结论却说反了，如“钓竿退货率 6.68%，是最低的”（其实是最高） |
| 可靠性 | 100% 确定，但不懂意思 | 懂意思，但本身也是模型，可能漏判或误报 |

审查员看不到写报告时的对话，角色只有“挑错”；可以在 `.env` 里设置 `REVIEWER_MODEL` 换成另一个模型。只改一次，防止写报告和审查来回拉扯；审查本身出错时只记录，不影响报告。

## 两种工作模式：规划-执行 / 工具调用

网页左侧可以切换。两种模式共用同一套安全检查、子进程执行、Skill 和数字核对。

| | 规划-执行模式（默认） | 工具调用模式（Function Calling） |
|---|---|---|
| 谁决定下一步 | 程序：先让模型列 3～5 步计划，再逐步写代码执行 | 模型：每一轮看结果，自己选下一个工具 |
| Skill 怎么加载 | 程序按数据状况和关键词自动选 | 模型调用 `load_skill` 自己加载 |
| 优点 | 流程固定、稳定、好调试 | 灵活，可以先看某一列再决定怎么算 |
| 风险与兜底 | 规划错了只能照做 → 程序去掉汇总步骤 | 可能绕圈 → 工具调用次数上限（默认 15 次），超限强制写报告 |

工具模式用 OpenAI 兼容接口的 `tools` 参数实现（DeepSeek 已实测支持），Agent Loop 是：

```
对话 + 工具清单 ──► 模型：“调用 X 工具，参数是……”
      ▲                     │
      │                     ▼
  结果作为 tool 消息    ToolBox 检查：工具存在吗？权限够吗？参数对吗？──► 执行
  放回对话 ◄───────────────────────────────────────────────────────┘
直到模型调用 submit_report，或达到调用次数上限
```

**工具与权限等级**（`analyst/tools.py`）：

| 权限等级 | 工具 | 怎么管 |
|---|---|---|
| 只读 | `preview_data` 预览数据、`describe_column` 查看某一列、`load_skill` 加载 Skill | 不改任何东西，直接执行 |
| 执行代码 | `run_python` 运行 Python | 先过 `sandbox.py` 静态安全检查，再放进子进程、有超时 |
| 结束 | `submit_report` 提交报告 | 报告交给 `validator.py` 核对数字出处 |
| 不提供 | 读写文件、联网、执行系统命令 | 工具箱里根本没有，模型想调也调不到 |

可以只开放部分等级（如 `allowed_levels={"read"}`），没开放的工具不会出现在工具清单里，强行调用也会被拒绝。

## 记忆：长对话压缩 + 长期偏好

| | 短期记忆（`ConversationMemory`） | 长期记忆（`PreferenceStore`） |
|---|---|---|
| 记什么 | 本次对话问过什么、结论是什么 | 用户的固定习惯，如“退货率按金额算” |
| 存多久 | 本次对话，清空对话就没了 | 本地 `memory/preferences.json`，下次打开还在（不上传） |
| 怎么控制长度 | 最近 3 轮保留原文；更早的由模型**滚动压缩**成一段摘要（保留品类名、最高最低、关键数字） | 同一主题只保留最新一条，网页侧边栏可删除 |
| 怎么用 | 追问时理解“那”“它”“最开始那个”指什么 | 放进规划、写代码、写报告的提示词；与 Skill 默认口径冲突时以偏好为准，并在报告里说明口径 |

说“记住，以后退货率都按金额算”就会被识别为偏好。只有出现“记住、以后、默认……”等词时才额外调用一次模型判断，普通问题不增加开销。

## 任务恢复：断点续跑

分析中途失败（断网、接口报错、程序被关掉）时，已完成的工作不会丢：

| 模式 | 存档内容 | 什么时候存 |
|---|---|---|
| 规划-执行 | 计划 + 已完成步骤的结果（含清洗后的数据） | 规划后、每一步完成后 |
| 工具调用 | 完整对话记录 + 已完成步骤 + 工具箱状态 | 每一轮工具调用之后 |

- 存档在本地 `outputs/checkpoints/<任务编号>.pkl`；任务编号 = 模式 + 问题 + **数据指纹** + 对话历史 + 偏好 的哈希，数据或问题变了不会误用旧存档；
- 先写临时文件再改名，存到一半崩溃也不会留下坏存档；存档损坏时自动从头开始；任务成功后删除存档；
- 网页上失败后会出现“从断点继续”按钮。

## MCP：既把工具开放出去，也能用别人的工具

```
本项目的 Agent（大脑：DeepSeek）──MCP 客户端──► 本项目的 MCP 服务器（数据分析工具 + 护栏）
                                        └──► 第三方 MCP 服务器（在 mcp_servers.json 里加一行）
Claude Code / Claude 桌面软件 ──MCP──► 本项目的 MCP 服务器（同一套工具也能给别人用）
```

| 角色 | 本项目的实现 | 作用 |
|---|---|---|
| MCP 服务器 | `analyst/mcp_server.py` | 提供工具，谁都可以连 |
| MCP 客户端 | `analyst/mcp_client.py` | 本项目的 Agent 连接 `mcp_servers.json` 里的服务器，读出工具清单交给 DeepSeek |

### Agent 作为 MCP 客户端

网页上选“工具调用”模式、工具来源选“MCP 服务器”（或评测时 `--mode mcp`）：

1. Agent 按 `mcp_servers.json` 启动服务器子进程，读取工具清单（名称、说明、参数格式、只读标记），转成 DeepSeek 的 `tools` 参数；
2. 模型要调用工具时，通过 MCP 转发给服务器执行，结果交回模型；
3. 数据由 Agent 存成临时 CSV 交给服务器加载，服务器只被允许读这个临时目录；
4. `run_python` 同时返回**文字**（给模型看）和**结构化数据**（指标、表格，给程序用），所以经 MCP 调用时，数字核对、独立审查、评测都和直接调用一样工作。

**接第三方工具时的权限**（别人写的工具不能无条件信任）：

| 情况 | 处理 |
|---|---|
| 工具标了只读（`read_only_hint`） | 直接开放 |
| 没标只读（可能改东西、删东西） | 默认不开放，在 `allow_tools` 里写明才开放；强行调用会被拒绝 |
| `hide_tools` 里的工具 | 不开放：`load_data` 由 Agent 统一调用；`analyze` 会让 Agent 调用自己；`verify_report` 和 Agent 自带的核对重复，开放后模型会反复核对、绕圈（实测过，见调优记录） |

评测：经 MCP 调用 14/14，和同时段直接调用（14/14）正确率相同，平均慢约 4 秒，主要花在每道题启动一次服务器上。

局限：MCP 模式下清洗后的数据保存在服务器进程里，存不进本地存档，所以这个模式不支持断点续跑；只连自己的服务器时比直接调用多一层进程间通信。

## MCP 服务器：让 Claude 也能用这套工具

[MCP](https://modelcontextprotocol.io/)（模型上下文协议）是 AI 应用连接外部工具的通用标准。`mcp_server.py` 把本项目的工具做成 MCP 服务器，Claude 桌面软件、Claude Code 等都能直接调用——此时“大脑”是 Claude，本项目提供工具和护栏。

| 工具 | 作用 | 权限 |
|---|---|---|
| `load_data` | 加载 CSV / Excel：默认示例数据；只允许 `sample_data/` 或环境变量 `ANALYST_DATA_DIR` 指定的目录 | 只读 |
| `data_overview`、`preview_data`、`describe_column` | 查看数据 | 只读 |
| `list_skills`、`load_skill` | 查看 / 加载 Skill（清洗规范、指标口径） | 只读 |
| `run_python` | 运行分析代码：安全检查 → 子进程 → 超时 | 不改动任何文件 |
| `verify_report` | 核对报告数字在本次计算结果里有没有出处 | 只读 |
| `analyze` | 让本项目的 DeepSeek Agent 完整分析一个问题（需要 `.env` 的 API Key） | 只读，访问模型接口 |
| `reset_data` | 撤销清洗，回到原始数据 | — |

不提供写文件、删文件、联网下载、执行系统命令的工具。每个工具都带 MCP 的 `read_only_hint` 等注解，客户端可以据此决定要不要先征求用户同意。

### 在 Claude Code 里使用

```bash
claude mcp add ecommerce-analyst -- C:\code\ai-data-analyst\.venv\Scripts\python.exe C:\code\ai-data-analyst\mcp_server.py
```

（路径换成你自己的项目位置。）然后在 Claude Code 里说“用 ecommerce-analyst 分析示例数据：各品类退货率是多少”，或输入 `/mcp` 查看连接状态。

### 在 Claude 桌面软件里使用

打开 设置 → 开发者 → 编辑配置，在 `claude_desktop_config.json` 里加入（路径换成自己的）：

```json
{
  "mcpServers": {
    "ecommerce-analyst": {
      "command": "C:\\code\\ai-data-analyst\\.venv\\Scripts\\python.exe",
      "args": ["C:\\code\\ai-data-analyst\\mcp_server.py"],
      "env": { "ANALYST_DATA_DIR": "C:\\Users\\你的用户名\\Documents\\订单数据" }
    }
  }
}
```

保存后完全退出并重启 Claude 桌面软件，对话框的工具菜单里会出现 ecommerce-analyst。`env` 一项可选：只有设置了 `ANALYST_DATA_DIR`，才能分析示例数据以外的文件。

## Skill（按需加载的专项规则）

每个 Skill 是 `skills/` 下的一个文件夹，`SKILL.md` 开头写“简介”（名称、什么时候加载），下面是具体规则。程序只在需要时把正文放进提示词。

| Skill | 什么时候加载 | 解决的问题 |
|---|---|---|
| [数据清洗](skills/数据清洗/SKILL.md) | 数据有重复、缺失、负数或极端值 | 按同类别中位数识别录入错误；剔除前后做对比；清洗后的数据全程共用 |
| [电商指标](skills/电商指标/SKILL.md) | 问题提到销售额、退货、广告、品类等 | 统一销售额、净销售额、退货率、ROAS、ACOS 的口径；不自行设计综合评分；比较类数字在代码里算 |

## 调优效果（同一个问题、同一份示例数据）

> 问题：“各品类的销售额和退货率分别是多少？哪个品类最值得重点投入？”

| | 第 1 次（基础版） | 加入数据清洗 Skill | 加入电商指标 Skill + 程序兜底 |
|---|---|---|---|
| 识别 6 条单价录入错误 | ❌ | ✅ | ✅ |
| 钓竿销售额占比 | 54.54%（被错误数据夸大） | 36.96% ✅ | 36.96% ✅ |
| 自行设计综合评分 | ❌ 有 | ❌ 有 | ✅ 不打分，按目标说明取舍 |
| 净销售额 / ROAS 等指标 | 无 | 无 | ✅ 有 |
| 用时 | 41.4 秒 | 32.5 秒 | 41.3 秒 |

详细过程见 [docs/调优记录.md](docs/调优记录.md)。

## 评测集（14 道题，自动打分）

`evals/cases.json` 里有 14 道题，覆盖核心分析、数据质量、业务指标、趋势、数据回答不了的问题、多轮追问、安全、简单问题、用户偏好、长对话压缩 10 类。每道题有自动检查标准（数字是否算对、报告是否包含/不能包含某些内容、是否加载对的 Skill、步骤是否失败、用时等），标准答案由 pandas 独立计算。

```bash
python evals/run_eval.py --label 这次改了什么
python evals/run_eval.py --mode tools --label 工具模式   # 评测工具调用模式
python evals/run_eval.py --mode mcp --label 经MCP调用    # 工具调用模式，工具经 MCP 服务器
```

| 轮次 | 通过 | 平均用时 | 改了什么 |
|---|---|---|---|
| 第一轮基线 | 9 / 12 | 33.9 秒 | — |
| 第二轮 | 12 / 12 | 25.8 秒 | 简单问题限制步数；报告不许自己做加减乘除；修正 1 道题过严的评测标准 |
| 第三轮：规划-执行模式回归 | 11 / 12（修正误判后 12 / 12） | 27.1 秒 | 核心流程未改；唯一未通过的 C01 是评测误判（报告写的是“未做综合评分”），已修正检查规则 |
| 第三轮：工具调用模式（新增） | 12 / 12 | 27.4 秒 | 新增 Function Calling 工具模式，模型自己选工具、自己加载 Skill |
| 第四轮：加入独立审查（规划-执行） | 12 / 12 | 26.0 秒 | 报告后增加审查员；修复“审查员看不到数据概况导致误判”的问题 |

| 第五轮：加入记忆（工具调用） | 13 / 14 | 24.6 秒 | C13、C14 通过；C01 为否定句误判，改进检查规则 |
| 第六轮：加入任务恢复（规划-执行） | **14 / 14** | 25.3 秒 | — |
| 第六轮：加入任务恢复（工具调用） | **14 / 14** | 23.5 秒 | — |
| 第七轮：工具经 MCP 调用（Agent 作为 MCP 客户端） | **14 / 14** | 29.7 秒 | 同时段直接调用对照 14/14、25.5 秒；多出的时间主要是每题启动一次服务器（约 3 秒） |

另有审查员专项评测（`python evals/run_review_eval.py`）：8 份人工报告，5 份故意埋了结论与数字矛盾的错误，审查员抓出 5/5，正确报告误报 0/3（题目少，只说明能抓住典型矛盾）。

任务恢复故障注入评测（`python evals/run_resume_eval.py`）：在第 4 次模型调用时故意断网，两种模式共 6 次全部从断点续上、报告完整。

每次的评测报告保存在 `docs/评测报告/`，分析过程见调优记录。

## 快速开始

需要 Python 3.11+ 和 Node.js 18+。

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
# 配置密钥：复制 .env.example 为 .env，填入 API Key（密钥只在后端使用，不会发到浏览器）
```

**方式一：只开一个端口（推荐日常使用）**——先打包前端，再启动后端，后端会同时提供网页：

```bash
cd frontend
npm install
npm run build
cd ..
uvicorn api.main:app --port 8000
```

打开 http://localhost:8000 ，点“使用示例数据”，点一个示例问题，或在底部输入框提问，之后可以继续追问。

**方式二：开发模式（改前端代码时用，保存后页面自动刷新）**——开两个终端：

```bash
uvicorn api.main:app --port 8000 --reload
```

```bash
cd frontend
npm run dev
```

打开 http://localhost:5173 ，前端会把 `/api` 开头的请求转发给 8000 端口的后端。

后端接口文档（FastAPI 自动生成，可以直接在网页上测试每个接口）：http://localhost:8000/docs

## 测试

```bash
python -m pytest -q
```

测试不需要联网和密钥，用 FakeLLM 按顺序返回预设回答，验证程序逻辑：
- 数据概况能识别缺失、重复、负数、极端值；
- 安全检查能拦截 `import os`、读写文件、访问双下划线属性等危险写法；
- 代码报错、死循环超时能正确处理；代码第一次写错列名时，能把错误交回模型并在第二次成功；
- 报告中编造的数字（如“预计增长 30.5%”）能被识别；
- Skill 只在需要时加载，并且确实进入了提示词；
- 第一步清洗后的数据会交给后续步骤；追问时上一轮的结论会带进提示词；
- “汇总”类的最后一步会被程序去掉；模型没按格式输出规划时有兜底；
- 工具模式：完整的工具调用循环能跑通；危险代码被拦下后模型改好重试；调用次数达到上限会停下并强制写报告；只读权限下不能运行代码、不存在的工具（如写文件）会被拒绝；清洗后的数据会被之后的工具使用；模型能自己加载 Skill；
- 独立审查：正确报告不改；严重矛盾会触发修改且审查意见交给写报告的模型；只有“提醒”不修改；审查员乱回答不影响报告；审查员可以是另一个模型；工具模式也会审查。
- 记忆：第 4 轮才压缩最早一轮、编号接着摘要往下数；压缩失败有兜底；偏好同主题覆盖、删除、重开文件还在；没有“记住/以后”等词不额外调用模型；偏好进入所有提示词；
- 任务恢复：断网后从第 2 步继续且不重新规划；换问题或换数据不复用存档；工具模式接着上次对话；存档损坏从头开始；
- MCP 服务器：工具清单和权限注解；危险代码被拦；报告核对；只能读授权目录；用 stdio 真实启动子进程并调用；
- MCP 客户端：第三方服务器的危险工具默认不开放、写进白名单才开放；按配置启动自己的服务器并调用；Agent 经 MCP 完成一次分析；结构化结果还原出指标和表格；
- 后端接口（`tests/test_api.py`）：配置接口不泄露密钥；提问时先推送进度再推送结果，报告和日志可下载；没有数据或参数不合法时拒绝；只说偏好时只保存不分析；上传 CSV 和拒绝其他文件类型；失败时提示可从断点继续；多轮后对话摘要生效。

模型的实际效果用真实模型运行评估，记录在调优记录里。

## 局限

- 安全检查是演示级别的防护，不等于真正的沙箱，请只分析自己的数据；
- 数字校验只能发现“找不到出处”的数字；独立审查能发现一部分结论矛盾，但审查员本身也是模型，可能漏判，结论仍需人工判断；
- 多轮对话：最近 3 轮带结论原文，更早的压缩成摘要，压缩可能丢失细节；每一轮仍从原始数据重新清洗和计算；
- 任务存档用 pickle 保存在本地，只应读取自己生成的存档；
- 分析效果依赖所选模型的能力。
